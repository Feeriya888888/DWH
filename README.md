# DWH-проект: аналитическое хранилище сети кофеен «Тёплое зерно»

Запускается одной командой без установки СУБД и без внешних зависимостей —
нужен только Python 3.8+. SQL написан в переносимом диалекте и легко
адаптируется под PostgreSQL (см. раздел «Перенос на PostgreSQL»).

## Бизнес-задача

Сеть кофеен фиксирует заказы в операционной системе, а аналитикам нужны
управленческие отчёты. Требования бизнеса:

- выручка по месяцам и категориям товаров;
- выручка по городам — при этом клиент может переехать, и заказ должен
  относиться к тому городу, в котором он жил **на дату покупки**, а не сейчас;
- данным можно доверять: в источниках бывают дубли и правки, а расхождение
  сумм между staging и хранилищем должно ловиться автоматически.

Классическая задача для Kimball-подхода — и она решена полностью, на данных,
которые специально содержат «подводные камни»: дубль заказа, обновление
цены товара, переезд клиента.

## Архитектура

```
операционная БД (имитация: CSV-выгрузки)
        │
        ▼
┌─────────────────────────────┐
│ STAGING (stg_*)             │  сырые данные, все версии строк,
│ имитация CDC + load_ts      │  дубли и правки сохраняются
└──────────────┬──────────────┘
               │  дедупликация (ROW_NUMBER по бизнес-ключу)
               ▼
┌─────────────────────────────┐        ┌──────────────┐
│ DWH: модель «звезда»        │◀───────│  dim_date    │
│                             │        └──────────────┘
│  fact_sales ────────────────┼──▶ dim_product (SCD1)
│        │                    │
│        └────────────────────┼──▶ dim_customer (SCD2)
└──────────────┬──────────────┘
               ▼
        контроль качества (DQ) → бизнес-отчёты
```

## Модель данных

| Таблица | Тип | Гранулярность / особенности |
|---|---|---|
| `stg_*` | staging | все версии строк источника + техническое время загрузки |
| `dim_customer` | измерение | **SCD Type 2**: каждая версия — строка с `valid_from`, `valid_to`, `is_current` |
| `dim_product` | измерение | **SCD Type 1**: изменённые атрибуты перезаписываются |
| `dim_date` | измерение | календарь, строится рекурсивным CTE, ключ формата ГГГГММДД |
| `fact_sales` | факт | грануляр «заказ × товар», суррогатные ключи, `unit_price` на момент продажи |

## Перенос на PostgreSQL

SQL практически переносим, меняется немногое:

- `STRFTIME('%w', d)` → `EXTRACT(ISODOW FROM DATE d)`;
- `DATE(d, '+1 day')` → `d::date + INTERVAL '1 day'`;
- скалярные подзапросы `MAX(sk)` для суррогатных ключей → `GENERATED ALWAYS AS IDENTITY` или sequence;
- CSV-загрузку из Python → `COPY ... FROM csv` или `COPY` в Docker-контейнере Postgres.

Логика SCD2, дедупликации, темпорального join и инкрементальной загрузки
переносится без изменений.
